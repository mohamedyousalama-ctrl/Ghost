# 02 — Collaboration Protocol Governance Mapping

**Status:** CP compatibility design record  
**Build authorization:** none

## 1. Governing separation

Ghost and the Collaboration Protocol are related but not identical.

- **Frozen CP v1.0.1** is an interaction-level accountability protocol.
- **Ghost** is a broader continuity, orchestration, and product system around CP.
- Ghost may add memory, cross-window continuity, scheduling, automation, recovery, and product UX.
- Those additions must not be described as frozen CP features unless a future CP version explicitly adopts them.

The architectural law is:

> **Continuity may propose and situate. Human authority confirms. The CP Guardian judges. External tools execute. Evidence reconstructs.**

## 2. Frozen CP objects in Ghost V1

### 2.1 Context

Frozen meaning: a bounded, declared or confirmed semantic and operational scope.

Ghost V1 use:

- each target Work Unit has exactly one active confirmed operational Context for the candidate action;
- a Context names inclusions, exclusions, constraints, permitted Agents, data boundaries, and lifecycle state;
- implicit merging between projects, people, companies, accounts, or LLM windows is forbidden;
- a provisional Context proposal may be generated by Ghost but cannot authorize action.

### 2.2 Intent

Frozen meaning: an explicit, verified declaration of what the user wants under defined constraints, bound to one Context.

Ghost V1 use:

- every target-specific Send requires an active verified Intent or a valid Automation Contract whose current trigger compiles into a target-specific Intent/action request;
- model confidence, memory, repeated behavior, or a previous approval does not create Intent;
- broad Human Objectives sit above CP and compile into separate target-specific Intent proposals;
- Intent remains revocable and must be revalidated immediately before dispatch.

### 2.3 Agent

Frozen meaning: a scoped executor or advisor with explicit permissions; it cannot self-authorize or modify its own permissions.

Ghost V1 use:

Each target LLM window is represented as a distinct Agent identity including:

- provider;
- account/workspace;
- conversation/window ID;
- model;
- tool/connectors available;
- role (`advisory`, `acting`, or `explanation-only` where applicable);
- current lifecycle state;
- permission and prohibition set;
- capability snapshot version.

A replacement model, new window, or changed tool set is a different or materially changed Agent and does not silently inherit authority.

### 2.4 Node

Frozen meaning: a user-committed structural constraint that governs future reasoning and action.

Ghost V1 examples:

- never merge to `main` without explicit approval;
- never send external messages from this project;
- do not expose credentials;
- use only the selected repository;
- preserve the original artifact before editing.

Nodes are binding only after explicit commitment and must be revised explicitly.

### 2.5 Pivot

Frozen meaning: a user-declared, non-binding epistemic marker of importance.

Ghost V1 use:

- mark a critical issue, uncertainty, change in direction, or insight;
- improve orientation and retrieval;
- never create permission or trigger execution by itself.

## 3. Responsibility Chain

Frozen chain:

```text
User Signal
  -> CP Verification
  -> AI Suggestion
  -> User Commitment
  -> Action
```

Ghost V1 must preserve every link for consequential Send.

### 3.1 Example

```text
User Signal:
"Keep the Claude Code review moving every five minutes."

CP Verification:
Clarify target window, allowed messages, forbidden actions, duration, and stop conditions.

AI Suggestion:
Proposed Automation Contract and target-specific Send grammar.

User Commitment:
Explicit approval of the exact contract.

Action:
A one-shot permitted status request is dispatched when the approved trigger becomes true.
```

No link may be skipped or compressed merely because the system is in Autopilot.

## 4. Guardian semantics

The frozen Guardian is read-only and returns exactly:

- `Allow`
- `Clarify`
- `Refuse`

Ghost product dispositions such as `Observe`, `Prepare`, `Hold`, `Dispatch`, or `Recover` are separate product-layer outcomes.

Correct mapping:

```text
CP Guardian decision:
Allow / Clarify / Refuse

Ghost runtime disposition:
Observe / Prepare / Hold / Dispatch / Recover / No Action
```

The Guardian must not:

- mutate Context, Intent, Agent, or permissions;
- execute the Send;
- create human authority;
- dismiss Friction;
- approve its own policy changes;
- become the connector or verifier.

## 5. Post-Classification checkpoint

Before Ghost builds a dispatch proposal, apply the frozen post-classification logic.

| Condition | Guardian result | Ghost behavior |
|---|---|---|
| signal/trigger is materially ambiguous | `Clarify` | create persistent Friction; do not dispatch |
| signal is outside the current Context | `Clarify` | ask user to confirm or move Context |
| action is requested without a Context | `Clarify` | require Context establishment |
| clear observation/no action requested | `Allow` | observe and update continuity only |

## 6. Pre-Execution checkpoint

Immediately before Send, Ghost must evaluate current state—not merely the state that existed when the Automation Contract was created.

At minimum check:

1. an Intent exists;
2. the Intent is verified and active;
3. the exact candidate message/action still matches the Intent;
4. the Context is open/current;
5. the exact target Agent is allowed in the Context;
6. the Agent is active;
7. the Agent type permits the proposed action;
8. the action is within Agent and connector permissions;
9. the action respects current Context constraints;
10. no unresolved Friction remains;
11. all required checks pass.

A failure must `Refuse` or `Clarify` according to the frozen semantics. Errors in the governance component must never default to `Allow`.

## 7. Friction

Frozen Friction triggers relevant to Ghost V1 include:

- `ambiguous_signal`
- `unverified_intent`
- `scope_boundary`
- `permission_violation`
- `high_risk_action`
- `missing_context`
- `conflict_detected`

Friction must:

- persist across five-minute cycles;
- remain attached to the correct Work Unit and Context;
- block relevant execution;
- be visible to the user;
- be resolved only by `user_clarified`, `user_confirmed`, `user_revised`, `user_abandoned`, or `system_blocked`;
- never expire silently into permission.

## 9. Historical/theoretical CP concepts used as threats or aids

### Silent Intent Inference (SII)

Use as a threat model:

- did Ghost choose a material meaning the user did not authorize?
- did a summary or previous model silently select the interpretation?

SII is not a frozen CP v1.0.1 object.

### Intent Pivot Point (IPP)

Use to detect material ambiguity while building a dispatch.

Record:

- original signal;
- candidate interpretations;
- material consequence;
- source Context;
- resolution method;
- selected interpretation;
- human authority where required.

IPP does not itself authorize execution.

### Context Roots

Use as provenance for why Ghost proposed a Context:

- current session;
- previous session;
- environmental/source system;
- no prior root.

A Context Root is not the frozen operational Context.

### ICD / IFI / SMP

These are historical or proposed constructs. They may inform experiments and UI, but they must not become uncalibrated hard authorization thresholds in Ghost V1.

## 10. Memory-is-not-authority implementation law

Every memory or Ledger item must state its authority effect explicitly.

Default:

```text
authority_effect = NONE
```

A memory may:

- help retrieve source material;
- propose a Context;
- identify an open loop;
- warn about a possible conflict;
- prepare a dispatch draft.

It may not by itself:

- open a Context;
- verify Intent;
- authorize Read or Send;
- broaden an Agent's permissions;
- resolve Friction;
- approve an action;
- promote a completion claim to verified truth.

## 11. Authority continuity after approval

An approval at time `t0` is a snapshot. Ghost must verify that it still covers the action at execution time `tN`.

Material invalidators include:

- payload/message drift;
- target-window drift;
- model/tool capability drift;
- Context drift or closure;
- destination/provider change;
- permission revocation;
- Agent substitution;
- new constraint;
- unresolved exception/Friction;
- expiry;
- handoff corruption;
- concurrent user change.

This is the central use of the current CP authority-continuity research in Ghost V1.

## 12. CP limitations that Ghost engineering must cover separately

Frozen CP does not fully specify:

- idempotency;
- duplicate/replay protection;
- distributed transaction atomicity;
- time-of-check/time-of-use races;
- state-version locking;
- delivery confirmation;
- partial-execution compensation;
- connector health and UI drift;
- cost budgets;
- model-to-model loop control.

These are required Ghost engineering extensions. They must be documented and tested without being misrepresented as existing frozen CP guarantees.

## 13. Conformance caution

Ghost must not claim CP v1.0.1 conformance merely because it:

- asks for confirmation;
- stores a prompt;
- displays a Guardian label;
- logs an action;
- has an approval button.

A conformance claim requires faithful representation and enforcement of the frozen object model, checkpoints, Friction, Responsibility Chain, stores, and logging semantics, plus executable conformance evidence.
